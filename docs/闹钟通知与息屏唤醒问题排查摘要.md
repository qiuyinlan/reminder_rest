# 闹钟通知与息屏唤醒问题排查摘要

这份摘要用于向 Android 开发者请教。重点问题是：应用安排的提醒在手机息屏或锁屏时，不能稳定显示通知、点亮屏幕、播放闹钟声音或持续振动。初稿记录时项目尚未上传 GitHub；后续修复、测试和交付状态见文末更新。

## 环境

- 应用：好好歇会，包名 `io.iftech.healthreminder`
- 测试手机：vivo V2073A
- 系统：Android 13 / API 33
- 初稿记录时的本地提交：`1e4f2da`（`Always post fullscreen alert when screen-off alarm is enabled`）
- 初稿记录时 HEAD 前的两次相关提交：`4841073`（息屏响铃改用前台服务）、`047a5c1`（提醒与息屏闹钟检查点）

## 观察到的问题

1. 手机息屏后，提醒经常没有通知、没有亮屏，也没有声音或振动。打开应用后，才看到提醒霸屏界面。
2. 表现不稳定：曾有第一次提醒成功、第二次失败，之后第三次又成功的情况；另有倒计时停在 `0s`、关闭再打开相关开关后暂时恢复的情况。尚未找到稳定复现规律。
3. 最近一次测试中，用户确认“没有通知，也没亮屏”。
4. 曾经有一份安装在手机上的测试包，安装时间约为 20:53。之后构建的“息屏提醒修复测试” APK 起初仅推送到手机下载目录；本次复测前已于 22:12:39 安装。安装后的效果见文末 22:16–22:20 真机日志记录。

## 已检查到的设备状态

在一次 ADB 检查中：

- 主用户下应用通知权限已授予，精确闹钟权限已授予。
- 提醒通知渠道的重要性为 HIGH；应用的息屏闹钟、振动设置和提醒规则均为开启。
- `dumpsys alarm` 中能看到应用登记的 `RTC_WAKEUP` / `AlarmClockInfo` 提醒。
- 一次失败测试附近的系统日志出现 `Displayed io.iftech.healthreminder/.ReminderActivity`（约 20:56:20）。这只能说明系统记录了 Activity 的显示/启动事件，不能证明当时屏幕从熄灭状态真正点亮、锁屏界面允许用户看见它，或通知成功发布。
- 设备上还发现 user 10 下的另一个应用副本，其通知重要性为 NONE。尚未确认用户是否使用该副本；目前不能认定它是问题原因。请确认测试时使用的 Android 用户/应用副本。

这些检查是某次测试时的快照，不代表每次失败时所有权限、渠道和电源管理状态都相同。

## 当前实现概况

- `ReminderScheduler` 使用 `AlarmManager` 创建提醒；息屏闹钟打开且精确闹钟可用时走 `setAlarmClock()`，其他情况按系统能力走精确空闲闹钟或允许空闲闹钟。
- 接收器 `ReminderReceiver` 收到提醒后读取屏幕交互状态和息屏设置。当前代码在息屏闹钟开启时继续发布提醒通知，并附带 `full-screen intent`。
- 息屏且用户开启铃声/振动时，接收器启动 `AlarmRingtoneService` 前台服务，由服务播放铃声并振动。新版源码增加了息屏响铃会话：息屏首响启动后，即使提醒将屏幕唤醒，后续周期仍维持闹钟铃声模式，直到用户处理或关闭提醒设置。
- `ReminderActivity` 配置了锁屏显示/点亮相关窗口属性。实际是否能在该机型、当前锁屏状态和系统策略下显示，仍需现场验证。
- 代码加入了 `HealthReminderAlarm` 日志，用于记录提醒触发时的屏幕状态、通知权限检查、服务启动结果和覆盖层结果。

## 尚未确认的原因

目前没有证据可以确定是单一原因。待排查方向包括：

- 广播接收器触发后，前台服务或 Activity 启动是否被 Android 13 / vivo 后台启动策略限制。
- 系统是否实际接受并展示了带 `full-screen intent` 的通知；应用侧调用通知 API 不等于系统一定显示通知或点亮屏幕。
- 锁屏通知显示、全屏通知访问状态、通知渠道的用户级设置或应用通知总开关是否在失败当时发生变化。
- 应用副本、用户配置、息屏/省电策略是否导致检查的权限状态与实际发提醒的实例不一致。
- 第二次及后续提醒是否都触发了接收器，是否每次都提交了通知，以及前台服务是否仍在运行或已被系统停止。
- 通知 ID、渠道 ID、PendingIntent 更新/取消、服务停止动作是否造成后续提醒被替换、清除或没有重新发出。

## 建议的下一轮最小复现记录

使用一个单独的短间隔测试提醒，不改动日常规则。每轮记录设备型号、Android/系统版本、当前 Android 用户、应用版本、提醒时间、息屏和锁屏状态，以及通知总开关、实际通知渠道、全屏通知访问状态、精确闹钟状态和电池限制状态。触发前后保存应用日志和以下系统快照：

```powershell
adb shell dumpsys alarm
adb shell dumpsys notification --noredact
adb shell dumpsys power
adb shell dumpsys deviceidle
adb shell dumpsys activity activities
adb logcat -d -s HealthReminderAlarm ReminderReceiver AlarmRingtoneService ActivityTaskManager NotificationService AlarmManager
```

每次都分别记录：接收器是否进入、`notify()` 是否调用、系统通知记录是否出现、前台服务是否启动、Activity 是否启动、屏幕是否亮起、铃声是否播放、振动是否持续。至少连续观察三次提醒，失败后立即抓取状态，避免只依据打开应用后的界面判断系统行为。

用户补充说明一直在使用 8 秒间隔的“实话实说”提醒测试。随后重新读取主用户（user 0）的实际偏好，确认该规则启用，`intervalSeconds=8`、时段为 09:00–23:00；`screen_off_alarm=true`、息屏振动开启。主用户通知权限和精确闹钟权限均已授予。user 10 下虽安装了应用副本，但该副本处于 stopped 状态且没有通知权限，不是本次测试使用的实例。

对照用户最初报告的“息屏时没有通知、没有声音或亮屏，打开应用后才看到提醒页”，本次是在同一台 vivo V2073A、Android 13、主用户 0 上，使用已经安装的版本和这条启用中的 8 秒规则重新验证。

使用当前已安装版本进行一次短时测试：通过 ADB 发送电源键关闭屏幕，等待约 24 秒后读取系统状态。测试期间系统记录了该应用的提醒广播投递；测试结束时观察到：

- 通知管理器中存在提醒 ID `703`，类别为 `alarm`，可见性为 `PUBLIC`，实际使用息屏闹钟通知渠道，渠道重要性为 `HIGH`。
- `AlarmRingtoneService` 正在运行并已进入前台，前台通知 ID 为 `4201`；服务 Intent 带有用户选中的铃声 URI。提醒通知渠道显示为静音是预期行为：服务成功启动后由服务负责播放声音，避免通知渠道重复播放。
- 顶层 Activity 为 `ReminderActivity`，窗口处于可见状态；系统显示 Keyguard 正在显示但被提醒页覆盖，内屏状态为 `ON`。
- 系统音频快照显示闹钟流未静音，音量设置值为 6。ADB 无法测量扬声器实际声压；用户随后确认本次提醒已经成功。

### 结论与更正

本次成功前没有修改项目源码、安装新包或调整通知/闹钟权限。成功的直接原因是这次用 ADB 关闭屏幕后等待了正在启用的 8 秒规则实际触发，并在主用户 0 上观察系统记录；这让“闹钟是否触发、通知是否提交、前台响铃服务是否运行、提醒页是否覆盖锁屏”逐项得到验证。当前版本和当时的设置能够跑通这条链路。

这不是一次代码修复，也不能据此确定之前每次失败的唯一原因或保证后续每次都成功。ADB 能确认服务已启动和闹钟流未静音，但扬声器实际出声由用户现场确认；单次成功也没有覆盖多次连续息屏测试。

前一轮把某次快照中的下一次提醒时间（次日 09:01）当作用户 8 秒测试失败的解释，是错误的概括。之后的实时偏好快照确认 8 秒规则启用，且系统按该规则继续登记并投递提醒。后续若再次失败，应在失败当下同时记录屏幕是否真正熄灭、`ReminderReceiver` 投递、通知实际渠道、`AlarmRingtoneService` 状态和 Activity/显示状态；不要再仅根据一次旧的下一次提醒时间判断原因。

## 同日再次失败与修复状态

约 21:51 的失败快照中，设备为 `Asleep`、`mInteractive=false`、屏幕 `OFF`；8 秒规则仍为启用状态，息屏闹钟也开启。但 `reminder_schedule` 中 `next_5` 是 21:50:49.852，已比快照时间落后约 45 秒；`dumpsys alarm` 里没有该 8 秒规则的待触发项，只剩次日 09:01 和 09:30 的日常提醒。闹钟统计最近一次投递约在 21:50:39。通知管理器还保留着 `id=703` 的息屏闹钟通知记录，但无法仅凭该记录判断它是否属于这次失败；当时没有证据证明当前这一轮唤醒了屏幕或启动了响铃服务。

这把问题范围缩小到：8 秒规则的下一次闹钟登记会在某次提醒后丢失，或没有成功恢复。它与之前成功的快照不同；当前数据仍不足以判定具体是谁取消了闹钟。

为降低提醒显示/响铃异常导致整条周期链停止的风险，源码已做以下调整：

- `ReminderReceiver` 先登记下一次周期，再处理通知；调度或通知抛出运行时异常时记录错误，不让通知失败直接跳过下一轮登记。
- Receiver 增加触发、规则检查、通知渠道和下次时间日志；响铃服务增加前台启动和铃声播放结果日志。
- 屏幕点亮时重新核对并登记提醒，作为 AlarmManager 条目丢失后的恢复入口。

修改后的 Debug APK 已本地构建成功。第一次安装尝试曾返回 `INSTALL_FAILED_ABORTED: User rejected permissions`；随后手机安装时间更新为 `2026-10-19 22:12:39`，确认新包已安装并运行。之后的真机日志可见新增的 `HealthReminderAlarm` 调试记录。

## 2026-10-19 新版再次复测

设备为 vivo V2073A / Android 13 / 主用户 0。新版安装后，规则“实话实说”（rule 5）仍设为 8 秒间隔；`screen_off_alarm=true`、息屏振动已开，铃声开关未单独写入偏好文件（代码默认开启）。

实时日志在 `22:16:55.094` 收到 rule 5，随后记录下次时间为 `22:17:03.100`。但下一条接收记录直到 `22:17:16.318` 才出现，中间约 21 秒；系统闹钟历史在 `22:16:56` 和 `22:16:57` 有取消记录。为什么 `22:17:03` 这一轮没有被接收，当前证据仍无法确定。

此后日志从 `22:17:26` 起连续记录了 rule 5 提醒，大致每 8 秒一轮，且每轮都有 `notificationPosted`。这些轮次都显示 `interactive=true`，并记录 `alarmMode=false`、`serviceStarted=false`、`sound=false`、`vibrate=false`；覆盖层也记录为 `overlayCovered=true`。系统通知记录显示这些事件走普通 `health_breaks_v2` 通道，而不是息屏闹钟铃声服务。因此这段复测中，周期提醒确实触发了，但没有启动专用闹钟铃声服务；它不能作为息屏响铃已修复的证据。普通通知通道是否实际发声，还受系统通知音量和设备状态影响。

在 `22:17:56` 的系统快照中，设备为 `mWakefulness=Awake`。应用覆盖层使用 `FLAG_KEEP_SCREEN_ON`，显示成功后会保持屏幕唤醒；由日志无法判定屏幕最初是被提醒界面唤醒，还是由用户操作唤醒，但后续铃声分流确实按“屏幕已亮”处理。到 `22:20` 快照时，rule 5 已关闭，`next_5` 已不存在，之后不再有该测试规则的待触发闹钟。

### 当前结论

这次复测把两件事区分开了：一是 `22:17:03` 附近存在一轮未见接收记录的间隔异常，原因未证实；二是后续约 8 秒周期正常触发，但设备处于亮屏交互状态，旧版代码因此不启动息屏闹钟铃声服务。覆盖层的 `FLAG_KEEP_SCREEN_ON` 会让已显示的覆盖层保持屏幕唤醒。

基于用户期待第二轮也能继续响铃，本地源码已改为记录“息屏响铃会话”：只有在提醒首次于息屏时触发且铃声或振动已启用时才开始会话；后续提醒沿用闹钟模式，即使屏幕已被提醒唤醒；处理、稍后或关闭相关提醒设置时清除会话。用户单纯手动亮屏、且没有活跃的息屏响铃会话时，仍使用普通通知模式。
