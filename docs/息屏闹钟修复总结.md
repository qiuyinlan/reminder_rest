# 息屏闹钟修复总结

日期：2026-10-19

## 原来是什么情况

8 秒周期提醒在息屏测试时表现不稳定：有时首轮或后续轮次没有响，有时响一轮后又不响。只看通知是否出现，无法分辨闹钟有没有触发、是否进入响铃服务，以及屏幕亮起后后续轮次走了哪条路径。

日志给出了关键分流证据：`22:48:33` 触发时设备已处于交互状态，且没有活跃的息屏响铃会话，因此按普通提醒处理，没有启动闹钟铃声服务；`22:48:47` 触发时屏幕熄灭，代码建立会话并启动前台服务，随后日志确认 `isPlaying=true`。这说明触发时的屏幕状态和会话状态会决定是否进入闹钟模式。ADB 实时日志是只读监听，不会启动响铃。

另一个明确的问题在服务实现：每次 8 秒提醒重新请求服务，旧逻辑都会先停止当前铃声再播放一次。循环铃声因此会被周期性打断或重启。早期快照里还出现过一轮没有接收记录、下一次 AlarmManager 条目缺失的情况，但当时没有证据确认是谁取消了闹钟；不能把它归结为同一个已证实原因。

## 现在怎样

- 首次提醒在息屏时触发、通过规则和使用状态检查，且启用了息屏闹钟与铃声或振动时，会建立按规则保存的响铃会话。屏幕随后被提醒界面唤醒，后续同一规则提醒仍沿用闹钟模式，直到用户处理、稍后提醒、划除提醒通知、关闭相关设置，或禁用/移除该规则。
- 前台铃声服务收到相同铃声 URI 和相同设置的重复请求时，会检查现有铃声是否仍在播放。若仍在播放，就保留现有播放，不再每 8 秒停止并重启；若播放已停止，后续请求仍可重新开始。
- 振动单独记录是否已尝试，设备没有振动器或振动调用失败时，不会因此打断正在播放的铃声。自选铃声无法播放时，会尝试默认闹钟铃声，并记录 fallback 的结果。
- 接收器先登记下一轮提醒，再发布通知；屏幕点亮时重新核对提醒登记。日志区分通知采用的实际全屏模式、服务启动请求是否被接受，以及服务内的播放结果。

## 为什么现在能响

代码修复针对两种已识别的失效路径：会话状态让首轮息屏提醒唤醒屏幕后，后续 8 秒轮次不会仅因 `interactive=true` 自动退回普通通知；重复请求处理则避免后续轮次把仍在循环的铃声停掉重播。实时 `logcat` 是只读的，不会替应用投递提醒或启动响铃服务；现有记录也没有构成“挂/不挂监听”的受控对照，不能把监听与成功建立因果关系。

用户已确认此前安装测试的会话与重复请求修订版能正常响铃。真机记录曾确认息屏轮次建立会话、前台服务启动且铃声进入 `isPlaying=true`；扬声器实际出声仍以用户现场听到为准。本次提交前又补充了异常隔离和诊断，重新构建的最终 APK 尚未安装，不能视为这份新 APK 已完成真机复测。曾有一轮调度条目缺失的具体触发原因仍未由旧日志证实，因此不能把所有历史失败都归为单一原因。

接收器依据前台服务启动 API 是否同步接受请求来选择静音通知通道；这不等于服务已确认播放。若服务在接受请求后仍启动或播放失败，应结合服务端错误日志和现场听感判断。
